## 1. 目的与边界

每类文档只回答一个问题，避免同一件事写在多处后互相漂移：

| 文档 | 回答的问题 | 权威范围 |
|---|---|---|
| [PRD](../prd.md) | 要什么、为什么做、做到什么程度 | 需求、范围、优先级、成功指标 |
| [架构](../architecture.md) / [ADR](../decisions.md) | 技术怎么做、为什么这样选 | 分层、模块、端口、存储、协议 |
| [前端设计](../frontend-design.md) | 界面长什么样、怎么交互 | 设计令牌、组件、状态、响应式、可访问性 |
| [Agent 协议](../agent-protocol.md) | Agent 如何接入、能做什么 | MCP 工具、能力位、权限、会话 |
| [路线图](roadmap.md) | 先做什么、现在什么状态、什么被暂缓 | 需求优先级、交付批次、暂存池 |
| 本文 | 怎么做开发、怎么评审、怎么验收 | 阶段、任务、门禁、变更控制 |
| [验收标准](../acceptance.md) | 做到什么算通过 | Given-When-Then、测试矩阵、发布门禁 |
| [发布规范](../release/) | 怎么发版 | 版本、流程、检查清单、发布说明 |

冲突处理：

- 需求是否成立、优先级多少，以 PRD 和用户裁决为准。
- 当前做什么，以路线图为准；路线图没有的事项默认不做。
- 技术方案以 ADR 为准；ADR 未覆盖的，先补 ADR 再实现。
- 是否通过，以验收标准为准；口头「看起来没问题」不算通过。

## 2. 角色与决策权

单人项目也要把「实现」和「验收」分开，避免自己给自己盖章。

| 角色 | 由谁承担 | 职责 | 不可越过的边界 |
|---|---|---|---|
| 产品负责人 | 用户 | 决定范围、优先级、验收、暂缓/纳入 | — |
| 实现者 | Claude | 读文档、实现、测试、自检、同步文档 | 不得自我验收 P0；不得擅自扩大范围 |
| 验收人 | 用户 | 按 AC 逐条验收，确认里程碑收口 | 未验收不得标「已完成」 |
| 发布负责人 | 用户 | 按发布规范决定发版 | 未过发布门禁不得发版 |

决策规则：

1. 需求冲突、优先级调整、暂缓与纳入，由用户确认后写入文档。
2. 技术选型与架构变更走 ADR，不以聊天结论代替。
3. 实现过程中发现的新问题，先分类（见第 7 节），再决定是修、是排、还是暂存。
4. Agent 可以提出建议，但不能替用户做范围与验收决定。

## 3. 生命周期总览

```text
S0 需求 → S1 设计 → S2 计划 → S3 实现 → S4 自检与评审 → S5 集成验收 → S6 收口 → S7 发布/维护
```

| 阶段 | 目标 | 主要输入 | 产物 | 出口门禁 | 负责人 |
|---|---|---|---|---|---|
| S0 需求立项 | 把想法变成可验收的需求 | 用户想法、缺陷、验收反馈 | PRD 条目 / 变更记录、AC、优先级 | 有 F-xx 或缺陷编号、有可测试 AC、优先级明确 | 用户 + Claude |
| S1 方案设计 | 确定怎么做、影响哪些模块 | PRD、架构、现有 ADR | ADR、架构/前端/协议文档更新、风险清单 | 设计文档同步；架构变更已有 ADR | Claude，用户确认 |
| S2 计划 | 拆成可执行任务并排入批次 | 路线图、设计文档 | 任务卡、批次范围、依赖清单 | 任务满足 DoR；已写入路线图 | Claude，用户确认 |
| S3 实现 | 完成代码、测试、文档 | 任务卡、设计文档 | 代码、单测、文档、CHANGELOG 条目 | 任务级门禁通过；自审完成 | Claude |
| S4 自检与评审 | 证明实现正确且未越界 | 代码、测试结果、AC | 自检记录、评审意见、缺陷清单 | 无 blocker/critical；用户评审通过 | Claude + 用户 |
| S5 集成验收 | 证明整个批次可用 | 验收标准、构建产物 | AC 逐条结果、冒烟记录 | P0 AC 全部通过；P1 有结论 | 用户 |
| S6 里程碑收口 | 形成可演示、可发布的批次 | 验收记录、CHANGELOG、路线图 | 版本准备、收口记录、文档同步 | 收口清单完成；路线图状态更新 | 用户 + Claude |
| S7 发布与维护 | 按规范发版并处理后续问题 | 收口产物、发布规范 | 发布包、发布说明、归档 | 发布门禁通过 | 用户 |

阶段可以回退：S3 发现设计不成立，回到 S1；S5 发现需求不清，回到 S0。回退必须记录原因，不能静默改范围。

## 4. 阶段详解

### 4.1 S0 需求立项

**入口**：新想法、需求变更、验收缺陷、Agent 使用反馈。

**活动**：

1. 判断是新增需求、需求变更、缺陷，还是暂缓项。
2. 在 PRD 中找到或新增 F-xx；写明用户价值、范围、不做的部分。
3. 补可测试的验收标准（Given-When-Then）。
4. 定优先级：P0 / P1 / P2。
5. 当前批次无法处理的，写入 [路线图暂存池](roadmap.md#7-暂存需求池)，分配 RM-xxx，不进入实现。

**产物**：PRD 变更记录、AC、路线图条目（或暂存条目）。

**退出标准**：

- [ ] 有唯一编号（F-xx 或缺陷编号）
- [ ] 说明用户价值与影响范围
- [ ] 标明优先级
- [ ] 有可测试的验收标准
- [ ] 明确本轮不做什么
- [ ] 暂不处理的已进入暂存池

### 4.2 S1 方案设计

**入口**：需求已通过 S0。

**活动**：

1. 判断影响面：domain / service / infra / handler / 前端 / 协议 / 存储。
2. 需要新端口、新依赖、新存储格式、协议变更的，先写 ADR。
3. 更新架构、前端设计或 Agent 协议中受影响的部分。
4. 列出风险与回退方案。

**产物**：ADR（如需要）、设计文档更新、风险清单。

**退出标准**：

- [ ] 影响模块与依赖方向明确
- [ ] 架构级变更已有 ADR
- [ ] 前端行为变更已写入前端设计
- [ ] Agent 工具/权限变更已写入协议
- [ ] 数据迁移或兼容策略明确（如涉及）
- [ ] 风险有对策

### 4.3 S2 计划

**入口**：设计已确认。

**活动**：

1. 把需求拆成任务卡：一个任务对应一个可评审的结果。
2. 标明需求编号、验收编号、影响文件/模块、依赖、测试方式。
3. 确认依赖已满足；未满足的不抢跑。
4. 把任务写入路线图当前批次；状态改为「进行中」。
5. 冻结当前批次范围；新想法走 S0，不直接插队。

**产物**：任务卡、批次范围、依赖清单。

**退出标准**：

- [ ] 每个任务满足 DoR（见第 12 节）
- [ ] 任务与 F-xx / AC 有映射
- [ ] 依赖已满足或已明确阻塞
- [ ] 不在当前批次的需求已进入暂存池

### 4.4 S3 实现

**入口**：任务满足 DoR，且当前批次未冻结范围。

**活动**：

1. 建分支（规则见第 9 节）。
2. 按分层规则实现；先写 domain 规则与端口，再接 infra。
3. 同步编写测试，不留「以后再补」。
4. 行为变化同步文档；更新 `CHANGELOG.md` 的 Unreleased。
5. 发现新需求或范围膨胀，停止实现，回到 S0。

**产物**：代码、测试、文档、CHANGELOG 条目。

**退出标准**：

- [ ] 代码符合分层与不变量
- [ ] 新增/修改逻辑有测试
- [ ] 文档与实现一致
- [ ] CHANGELOG 已记录
- [ ] 无未规划的功能夹带

### 4.5 S4 自检与评审

**入口**：实现完成，任务级门禁可运行。

**活动**：

1. 运行任务级门禁（见第 8 节），保留输出。
2. 按自审清单逐项检查（附录 14.4）。
3. 用户评审：看 diff、看演示、按 AC 抽查。
4. 缺陷分级：blocker / critical / major / minor；blocker 与 critical 必须清零才能进入 S5。

**产物**：自检记录、评审意见、缺陷清单。

**退出标准**：

- [ ] 任务级门禁全部通过
- [ ] 自审清单完成
- [ ] 用户评审通过
- [ ] 无 blocker / critical
- [ ] major 已有处理结论

### 4.6 S5 集成验收

**入口**：任务评审通过，批次功能已集齐。

**活动**：

1. 按 [验收标准](../acceptance.md) 逐条执行对应 AC-Mx-*。
2. 执行 P0 功能验收与手工冒烟。
3. 在干净 Windows 上验证绿色版：不写 AppData、日志在 exe 目录、WebView2 正常。
4. 回归相邻功能，确认没有破坏既有链路。
5. 记录每条验收的证据（截图、日志、导出文件）。

**产物**：AC 逐条结果、冒烟记录、缺陷清单。

**退出标准**：

- [ ] P0 对应的 AC-Mx-* 全部通过；P1 已完成或已明确转入暂存池
- [ ] P0 功能验收通过
- [ ] 绿色版检查通过
- [ ] 无 blocker / critical
- [ ] 证据可追溯

### 4.7 S6 里程碑收口

**入口**：S5 通过。

**活动**：

1. 按 [版本管理](../release/versioning.md) 确认版本号与 `VERSION`。
2. 更新 CHANGELOG：把 Unreleased 内容归入对应版本。
3. 更新路线图状态：当前批次「已完成」，下一批次解除阻塞。
4. 同步所有受影响文档（见第 10 节）。
5. 产出可演示版本，执行里程碑收口清单（附录 14.2）。
6. 逐条评审暂存池：保持暂存、评估、规划、纳入或关闭。

**产物**：版本号、CHANGELOG、路线图状态、收口记录、演示版本。

**退出标准**：

- [ ] 版本一致性检查通过
- [ ] CHANGELOG 已归档
- [ ] 路线图状态与证据一致
- [ ] 文档同步完成
- [ ] 暂存池已评审
- [ ] 用户确认收口

### 4.8 S7 发布与维护

**入口**：S6 收口完成。

**活动**：

1. 移交 [发布流程](../release/release-process.md)，按发布检查清单执行。
2. 发布后收集问题，按缺陷流程处理。
3. 阻断性问题走 hotfix；不夹带新功能。
4. 维护期变更仍走 S0，不直接改已发布产物。

**产物**：发布包、发布说明、归档记录、后续问题清单。

**退出标准**：以发布门禁与发布检查清单为准，本文不重复。

## 5. 里程碑工作分解

> 本节保留现行 M2 与原后续批次的任务基线。新目标的节点模型、自动建节点和云端 Agent 见 [PRD 1.1](../prd.md#11-新目标需求草案未实现) 与 ADR-027/028；何时切换由用户决定，不能把旧任务/旧验收当作新目标已完成，也不能在决定前按旧任务继续实现与新目标冲突的行为。

里程碑是**交付批次**，不代表日期。批次顺序由依赖决定；同一批次内先做 P0，再做 P1。

## 6. 推进方式

- **按优先级拉取**：从路线图取当前批次任务，P0 未完成不做 P1，P1 未决不做 P2。
- **按依赖推进**：前置批次未收口，不开始依赖它的批次；独立任务可并行，但各自满足 DoR 与门禁。
- **不设日期与工时**：不写日期计划、不承诺完成时间、不用「还剩几天」判断进度；进度只看门禁与 AC。
- **范围冻结**：批次开始后冻结范围；新想法进入暂存池，不在实现中插队。
- **一次只收口一个批次**：同一时间只对一个里程碑做 S6，避免版本与文档交叉。
- **事件驱动评审**：任务完成、批次收口、发版前、出现阻塞时评审；不按日历开会。
- **停止规则**：门禁无法通过时，标记「阻塞」，写清原因与需要的决策；由用户选择调整设计、拆分、暂缓或停止。

## 7. 变更控制

开发中出现的变动，先分类，再决定写到哪里。**不允许静默变更。**

| 类型 | 判定 | 处理 | 写入位置 |
|---|---|---|---|
| A 范围内修正 | 不影响需求、AC、架构，只是实现细节 | 直接改，补测试 | CHANGELOG（必要时） |
| B 需求变更 | 改变行为、范围、验收或优先级 | 用户确认；更新 PRD 与 AC；影响批次则更新路线图 | PRD 变更记录、验收标准、路线图 |
| C 暂缓 | 当前批次不做，但值得保留 | 分配 RM-xxx；不写实现代码 | [路线图暂存池](roadmap.md#7-暂存需求池) |
| D 紧急缺陷 | 阻断使用或数据安全 | 立即修复；走 hotfix 分支；记录原因与影响 | CHANGELOG、发布说明、路线图（如影响范围） |

决策顺序：

1. 是否改变已验收行为？否 → A。
2. 是否能在当前批次范围内完成？是 → B（记录范围变化）；否 → 3。
3. 是否必须现在做？否 → C；是 → 4。
4. 是否改变架构或契约？是 → 先补 ADR，再走 B；否 → B 并调整批次。

暂存池纪律：

- 入池不等于拒绝，也不等于承诺。
- 入池必须由用户确认，写清暂缓原因与触发条件。
- 池中条目不得直接开工；纳入必须先回到 S0。
- 每个里程碑收口时逐条评审，避免池子腐烂。

## 9. 分支与提交

- `main` 始终保持可构建。
- 分支命名：`feat/Mx-短描述`、`fix/短描述`、`docs/短描述`、`hotfix/x.y.z`。
- 跨模块、重构、协议变更必须用分支；单文件文档修正可直接在 `main`。
- 提交信息使用 Conventional Commits：`type(scope): 简述`，type 取 `feat|fix|docs|refactor|test|chore|build`。
- 一个提交只做一件逻辑上的事；不混入格式化、无关重命名、生成物。
- **禁止**任何 `Co-Authored-By`、`Co-authored-by` 或其他署名/致谢尾注。
- 未经用户要求不执行 commit / push；用户要求提交时，确保门禁通过。
- 发布 tag 只由发布流程创建，不在开发中随手打 tag。
- 不提交 `data/`、`logs/`、`webview2/`、构建产物、密钥。

## 11. 任务跟踪

不引入 issue 系统。跟踪以三个锚点为准：

1. **需求编号**：F-xx。
2. **验收编号**：AC-xx / AC-Mx-y。
3. **路线图状态**：批次与暂存条目。

任务卡字段：

| 字段 | 说明 |
|---|---|
| 任务 ID | `Mx-yy` |
| 目标 | 一句话说清完成后的可观察结果 |
| 需求 | F-xx |
| 验收 | AC-xx / AC-Mx-y |
| 影响 | 目录、模块、协议、存储 |
| 依赖 | 前置任务或外部条件 |
| 测试 | 单测 / 回放 / golden / 手工 |
| 风险 | 失败模式与回退 |

状态只在门禁有证据时变更；不以「写了多少代码」判断进度。若任务拆为可独立验收的子项，应分别记录子项状态与证据；原任务须等所有子项都经用户验收后才标记「已完成」。
