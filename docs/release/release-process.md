# 发布流程

## 1. 角色

单人项目也要分职责，避免"自己觉得没问题"：

| 角色 | 职责 |
|---|---|
| 版本负责人 | 范围、进度、质量、最终发版决定 |
| 发布协调 | 组织检查、冻结变更、归档记录 |
| 测试 | 执行验收与冒烟 |
| 支持 | 整理已知问题与复现步骤 |

小团队可由同一人兼任，但检查项必须逐条确认。

## 2. 节奏

- 常规：按里程碑发 MINOR；每个里程碑一个 0.x 版本。
- 修复：发 PATCH；不夹带新功能。
- 热修：阻断性问题随时发，走简化流程但不跳过记录。

## 3. 流程

### 3.1 计划与冻结

输入为开发流程 S6 的收口产物：验收记录、CHANGELOG、路线图状态、文档同步结果。见 [开发流程](../dev/process.md)。

1. 确定版本号与范围。
2. 产出「版本内容清单」。
3. 范围冻结后，新增变更需记录原因与影响。
4. 更新 CHANGELOG 的 Unreleased。

### 3.2 构建

1. 干净工作区；无未提交改动（除版本号与 CHANGELOG）。
2. 构建前端、后端、运行时资源。
3. 注入版本号。
4. 组装绿色包：
   ```
   audio-ui-vX.Y.Z-win64/
   ├── audio-ui.exe
   ├── runtime/
   ├── docs/
   ├── checksums.txt
   └── README.txt
   ```
5. 生成 SHA-256；可选病毒扫描。
6. 禁止使用个人临时脚本替代标准流程。

### 3.3 测试

1. 单元、集成、协议回放、golden frame。
2. 干净 Windows 冒烟。
3. 绿色版检查：不写 AppData、日志在 exe 目录、WebView2 正常。
4. 手工验收 P0 用例。
5. 缺陷分级：blocker / critical / major / minor；blocker 必须清零。

### 3.4 候选与发布

1. 打 `alpha` / `beta` / `rc` 标签。
2. RC 只接受 blocker 修复。
3. 创建 annotated tag `vX.Y.Z`。
4. 创建 Release，上传 zip 与 checksums。
5. 发布说明按模板填写，客户版与内部版分开。
6. 不建议在产物未验证前创建正式 Release。

### 3.5 发布后验证

1. 下载链接可访问。
2. 解压后双击可启动。
3. 版本号显示正确。
4. 日志生成在 exe 目录。
5. 至少一条完整链路可用。
6. 归档发布记录、检查清单、发布说明。

## 4. 热修复

1. 从对应 tag 建 `hotfix/x.y.z`。
2. 只修阻断问题。
3. 走 PATCH 版本与精简检查清单。
4. 修复后回合主干。
5. 发布说明注明基于哪个正式版本、修复范围、升级前提。

## 5. 文档同步

每次发布检查：

- README 的版本与下载链接。
- 文档中的命令、路径、截图。
- CHANGELOG。
- 发布说明。
- `.mcp.json` 示例与协议版本。
- 安装/运行说明。

## 6. 回滚

- 保留上一版本 zip 与 checksums。
- 数据格式不兼容时，回滚需同时回滚数据或使用迁移。
- 回滚后在 CHANGELOG 记录原因与影响。

## 7. 禁止事项

- 未验证产物就创建正式 Release。
- 发布说明使用旧版本号、旧文件名、旧路径。
- 夹带未评审变更。
- 用个人脚本替代标准构建且不更新文档。
- 移动或覆盖已发布的 tag。
